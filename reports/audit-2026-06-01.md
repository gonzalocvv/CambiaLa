## 4. Hallazgos por severidad

### 🔴 Crítico

**H1 — El HANDOFF/BACKLOG ocultan que el camino crítico del MVP ya está desbloqueado.**
Todas las entradas del HANDOFF (Corridas 8–17) repiten `S0.7 🔒 Supabase — toda la capa de Auth bloqueada`. Es falso: Supabase está provisionado, migrado y seedeado. Resultado: el auto-builder evitó Auth (RF-101–107), Onboarding (RF-108–111) y el marcado de álbum (RF-203/206/208) durante ~9 corridas, trabajando en ítems de menor prioridad. **Sin Auth, ninguna feature construida (matches, notificaciones) es usable de punta a punta.**
_Acción:_ liberar S0.7 (hecho en este PR), corregir el HANDOFF (hecho), y apuntar la próxima corrida a implementar la base de Auth (cliente `@supabase/ssr` + `getSession()` real). Solo RF-102 (Google) queda pendiente de config de dashboard.

### 🟠 Alto

**H2 — `getSession()` es un stub `return null`** (`src/lib/auth.ts:8`).
Toda ruta autenticada (`/api/matches*`, `/api/notifications*`) y la página `/matches/[id]` devuelven 401 / "no autenticado" para **todos**. Es esperado pre-auth, pero combinado con H1 significa que el feature set construido está inerte. Ahora que Supabase está listo, esto es implementable ya (no bloqueado).

**H3 — Servicios de runtime sin keys → no-ops silenciosos en prod.**
Con `INNGEST_*`, `RESEND_API_KEY`, `SENTRY_DSN`, `NEXT_PUBLIC_POSTHOG_KEY` vacías: no hay recálculo async de matches (RF-307), ni limpieza programada (RF-309), ni emails (RF-406), ni monitoreo de errores, ni analytics. Los placeholders de host/org/project dan falsa sensación de "configurado". Correctamente 🔒, pero conviene tenerlo explícito antes de cualquier launch.

### 🟡 Medio / Menor

**H4 — String hardcodeado en JSX** (`src/app/matches/[id]/page.tsx:31`): `partner.username ?? partner.name ?? 'Usuario'`. El `match-card.tsx` usa `t('unknownUser')` para lo mismo. Viola "cero strings hardcodeados en JSX" de CLAUDE.md e introduce inconsistencia i18n.

**H5 — Link de navegación muerto**: `/matches/[id]` linkea "volver a matches" → `/matches` (`page.tsx:39`), ruta de listado que **no existe** como página (RF-310 entregó solo la API). Click → 404.

**H6 — `postcss <8.5.10`** (vuln moderada, transitiva vía `next`). Build-time. Resolver con `pnpm.overrides` o bump de Next.

**H7 — Servicios importan tipos de Prisma** (`import type { Match }` en `match.service.ts:1`, `{ Notification }` en `notification.service.ts:1`). Es type-only y se usa para mapear a DTOs, pero acopla la capa de servicio a Prisma. Bajo impacto; considerar tipos de dominio propios si se quiere desacoplar del todo.

**H8 — `avatarUrl` inyectado en CSS inline** `url(${partner.avatarUrl})` (`matches/[id]/page.tsx:51`, también en match-card). Riesgo bajo (set vía CSSOM, no HTML; `url(javascript:)` no ejecuta). Cuando se implemente la subida de avatar (RF-112), validar/allowlistear el host de la URL. Sin riesgo vivo hoy (0 usuarios).

**H9 — `CLAUDE.md` ajeno en el directorio padre**: `/Users/gonzalocabrera/Desktop/CLAUDE.md` es de otro proyecto (IngSoft-DA2 / DarkKitchen, .NET "Obligatorio 2"). Se carga como instrucción de proyecto por herencia de directorio y puede confundir a agentes/tooling. No es un problema del repo, pero conviene saberlo.
